# Conversation ingest

The daemon indexes clyde's conversation corpus as a document-kind codebase with canonical path `chat:///<collection id>` and one Milvus collection per corpus. The same pipeline indexes any registered document collection through the generic item RPCs. This page explains the ingest pipeline as it works today and links each behavior to the code and test that own it.

## Manifest contract

A client sends the full manifest of per-item fingerprints every pass. The engine compares the manifest with the collection's Merkle checkpoint and replies with the new and changed item ids. The client then streams content for only those ids. clyde uses `SyncConversationManifest` and `UpsertConversationDocumentsStream`, where the item id is the conversation id. A generic client uses `SyncCollectionManifest` and `UpsertCollectionItemsStream` (`proto/lmsemanticsearch/v1/service.proto`) against a collection it registered with `RegisterCollection`. The generic RPCs never register a collection implicitly and fail with `NotFound` for an unregistered collection id.

The needed reply is capped. `capNeededConversations` (`internal/daemon/manager_conversations.go`) returns at most `Config.MaxConversationsPerIngest` ids per reply (default 100, zero disables). Modified items always fit before added ones. The added window rotates behind a per-codebase cursor, and every id eventually enters a reply. Both manifest RPCs share this cap and cursor. `TestSyncConversationManifestCapsNeededReply` and `TestSyncConversationManifestRotatesModifiedOverflow` (`internal/daemon/manager_conversations_test.go`) pin the cap and the rotation, and the cap bounds every ingest job regardless of backlog size.

The Merkle checkpoint stays at item granularity: one entry per item id with the manifest fingerprint. The checkpoint matches the client's wire manifest one to one.

## Generic item rows

A generic upsert stream sends one header frame first, then rows frames, then at most one manifest frame last. The engine rejects a frame out of that order, a rows frame with more than 1024 rows, and a stream with more than 512 MiB of row bytes. The gRPC message size limit bounds each frame. Each row sets a `row_key`, an `item_id`, text, and typed scalar values for declared columns. An unset scalar value is null.

The engine validates every row against the collection's saved declaration before it queues a job. It rejects an undeclared column, a column set twice, a value of another type, a null or missing value for a column that is not nullable, a string longer than the declared maximum, a duplicate row key, and an item id column value that differs from `item_id`. A rejected column appears in the `ErrorInfo` metadata key `column`. The engine stores `item_id` in the declared item id column.

The engine stores `row_key` as the row's relative path. Text longer than the 60000-byte split budget stores parts keyed `row_key/0`, `row_key/1`, and so on, with the same primary-key derivation as conversation rows. A row's `continuation_prefix` starts every part after the first with the prefix and a newline, in every collection. A non-empty prefix shorter than the split budget lowers the budget by the prefix length plus one, and the engine splits the text at that lowered budget. An empty prefix changes nothing. The conversation RPC splits a tool call row through the same code with the trimmed tool name as the prefix.

The header's reconcile mode applies to an item the manifest omits. `RETAIN`, the default, keeps the item and its rows. `AUTHORITATIVE` removes the item's rows by the declared item id column and requires a manifest frame. Without a manifest frame, a retain upsert fingerprints each delivered item from its rows.

A collection registered with the conversation declaration stores generic rows in the conversation schema. A registered declaration matches the conversation declaration when it has the same item id column and the same columns, types, nullability, and string lengths in any order. The conversation RPC and the generic RPC then write identical rows, vectors, and checkpoints for the same transcript. `TestGenericCollectionIngestParity` (`test/live/generic_collection_ingest_live_test.go`) checks that equality against a real Milvus database. The engine stores the provider derived from the conversation id and rejects a row with a different provider value. A row key in such a collection must be `conv/<item_id>/<messageIndex>`, `convtool/<item_id>/<messageIndex>/<tool>`, or `convthink/<item_id>/<messageIndex>`, with the same message index as the row's `messageIndex` value. A client stores a tool call row exactly as the conversation RPC does when it sends the same row text with the trimmed tool name as `continuation_prefix`, or an empty prefix for a tool call without a name.

## Scalar backfill and item delete

`BackfillCollectionScalars` fills declared scalar columns on stored rows without embedding them again. The header lists the columns to fill, and each items frame sets one value for every listed column of one item. A row needs the backfill when one listed column is null or an empty string on the row. The engine writes an item's value only into those null or empty columns. Every other column, the text, the row key, the vector, and the Merkle checkpoint stay as stored. On Milvus, a partial update writes only the listed columns. The reply counts `changed` rows of streamed items and `orphan` rows of items the stream omits, and the backfill leaves orphan rows unchanged. A dry run returns the same counts and writes nothing.

The engine rejects a listed column that is undeclared, listed twice, the item id column, or a bool or int64 column that is not nullable. It rejects an item value that is undeclared, mistyped, oversized, null, set twice, or absent for a listed column. A rejected column appears in the `ErrorInfo` metadata key `column`. In a collection with the conversation declaration, the engine derives `provider` from the item id and `messageIndex` from the row key, and it rejects both as listed columns.

`DeleteCollectionItem` queues a job that removes one item's rows by the declared item id column. The job leaves the Merkle checkpoint unchanged, and a later manifest sync converges it. While another job of the collection is queued or running, a delete fails with `FailedPrecondition` and `ErrorInfo` reason `active_job_conflict`, and the metadata key `active_job_id` stores that job's id. `TestDeleteRefusalReportsActiveJobConflict` pins this refusal on both delete RPCs.

In a collection with the conversation declaration, both operations also select rows without a `conversationId` value by their `conv/`, `convtool/`, and `convthink/` path prefixes. Rows written before the column existed have that shape.

Both generic RPCs apply the maintenance mode refusal before they resolve the collection or queue a job. They fail with `NotFound` for an unregistered collection id.

`BackfillConversationScalars` runs the same backfill on `workspaceRoot` and `archived`, and `DeleteConversation` queues the same delete. Both keep their wire contracts and their maintenance refusal, and both register a missing conversation collection the way every conversation RPC does. `TestBackfillCollectionScalarsMatchesConversationBackfill` and `TestDeleteCollectionItemRemovesOnlyThatItem` (`internal/daemon/grpc_server_collection_maintenance_test.go`) pin this behavior on the local vector store. `TestGenericCollectionMaintenanceParity` (`test/live/generic_collection_maintenance_live_test.go`) pins it against a real Milvus database.

## Row family delta

A delivered item embeds only its absent row families. A row family is one client row, one conversation message's text, one tool call, or one conversation message's thinking, together with every split part of it. `collectionItemSource.indexOne` (`internal/daemon/collection_item_source.go`) reads the stored rows of every delivered item once per job and emits the chunks of each family with no usable stored row. A stored row is usable when its content is not blank. The job removes no rows for a changed item. A stored family keeps its content when the delivery changes its text. An appended message, tool call, or client row inserts, and a stored message absent from the delivery stays. `TestConversationIngestAppendsOnlyMissingRows` (`internal/daemon/manager_conversations_test.go`) and `TestUpsertCollectionItemsBackfillAndForce` (`internal/daemon/grpc_server_collection_stream_test.go`) pin this behavior.

A conversation collection reads stored rows through the conversation batch read. That read matches a message text family by message index and selects rows written before the `conversationId` column existed by their `conv/`, `convtool/`, and `convthink/` path prefixes. A generic collection reads stored rows by its declared item id column.

Two header flags change the delta. `backfill_delivered` forces each delivered item with an absent family into the job even when its fingerprint is unchanged, judged from stored rows without generating chunks. For a conversation, backfill checks only tool call and thinking families, whether conversation documents or rows of a collection with the conversation declaration deliver it. A backfill does not select a conversation for an absent or blank stored message text row. `force_reexamine` replaces every delivered item's rows with vector reuse disabled. When both flags are set, force wins.

The delta uses the generic per-item override fields on `indexer.OneFileResult` (`internal/indexer/indexer.go`), which `handleChangedFile` (`internal/daemon/manager_delta.go`) applies. A fully unchanged delivery advances the checkpoint with zero Milvus writes.

## Seed and reuse invariants

`resolveSeed` (`internal/daemon/seed.go`) is the only seed decision, and its doc comment states the invariant that a seed may only cause skips for rows provably present in the collection the build writes to. `resolveItemReusePolicy` (`internal/daemon/reuse_policy.go`) is the only reuse decision. A build reuses the vectors of an existing live collection regardless of staging target or codebase kind, and only a forced job opts out. `TestRunBootstrapReusesLiveCollectionVectors` and `TestRunBootstrapMissingLiveCollectionEmbedsEverything` (`internal/daemon/manager_bootstrap_test.go`) pin both sides. A bootstrap over an already-populated corpus reuses its vectors instead of re-embedding it.

## Collection evidence and bootstrap reasons

Routing decisions judge the stored collection name, never a re-derived one. `probeCollectionEvidence` (`internal/daemon/collection_evidence.go`) returns presence plus row-count evidence, and `decideEmptyDiffMode` (`internal/daemon/collection_policy.go`) sends an empty-diff job to bootstrap only on definitive evidence. `TestConversationEmptyDiffStoredNamePresentCompletesNoop` (`internal/daemon/manager_conversations_test.go`) pins the incident regression where a populated collection was treated as missing.

Every job that routes to bootstrap records why. `routeToBootstrap` (`internal/daemon/manager_jobs_state.go`) owns the reason vocabulary and stamps `Progress.BootstrapReason`, which persists in the job ledger. The job record alone then explains an unexpected full rebuild.

## Typed collection search

`SearchCollection` searches a registered collection with a typed filter tree instead of a raw vector store expression. The request has a collection id, a query, a limit that defaults to 10, a `min_score` floor, an optional `group_by` column with a `per_group_limit` cap, and an optional `CollectionFilter`. A filter node is `all_of`, `any_of`, `negate`, or a leaf: `equals`, `in_set`, `range` with an inclusive `lower` and an exclusive `upper` on an int64 column, `is_null`, or `is_present`. Time columns store Unix seconds as int64. The daemon validates every filter and group column against the saved declaration before it loads the collection or runs the query. An undeclared column, a literal of the wrong type, a range on a non-int64 column, a tree deeper than 16 levels, and a membership set larger than 65,536 values fail with InvalidArgument, and a column violation sets the ErrorInfo metadata key `column`. An unregistered collection fails with NotFound. Maintenance mode fails the search before any collection work.

A comparison on a null value never matches, and `negate` does not turn it into a match. Only `is_null` and `is_present` select on null values. Milvus and the offline store apply the same three-valued rule.

Each hit returns its `row_key`, the stored `relativePath`, with its content, score, and one `CollectionHitScalar` per declared column in declaration order. A scalar sets `null_value` for a stored null and sets no value when the stored row has no such column. For a conversation collection, the scalars include `loadRules` and the lowercased `role`.

Each search embeds the query once and runs one ranking search with the whole tree applied natively. Every `in_set` leaf binds its values as one Milvus expression template parameter, so a scope of any size runs as one search. A hybrid collection runs both legs and the RRF fusion at a fixed depth of 16,384 rows, and a dense collection runs one search at the same depth. The depth never depends on the limit, the cap, or the floor. The ranking returns only each row's primary key, `relativePath`, group column, and score. The daemon sorts it by descending score, then ascending `relativePath`, then ascending primary key, and walks it once to apply the score floor, the group cap, and the limit. It then reads content and every declared scalar for the selected rows by primary key. One query and request therefore return the same rows in the same order on every call, and a smaller limit returns a prefix of a larger one. Rows with a null or absent group value share one group, except in a conversation collection grouped by `conversationId`: a row with a null `conversationId` groups by the conversation id in its legacy metadata, the identity the per-conversation cap used before the scalar columns existed. The offline store ranks at the same fixed depth with the same order and tie-break. When at most 16,384 rows match the filter, it scores every matching row exactly. Otherwise it ranks the 16,384 nearest rows from its HNSW index and applies the filter while it walks them.

`GetCollectionItemState` returns an item's fingerprint from the Merkle checkpoint. An unknown item and an unregistered collection return an empty fingerprint.

`SearchConversations` and `SearchWithinConversation` keep their wire contracts and run through the same search. The conversation filter becomes a top-level `all_of`: providers, workspace roots, and lowercased roles become `in_set` leaves, conversation ids become an `in_set` on `conversationId`, the parent becomes `equals`, `from_unix` and `message_index_from` become inclusive lower bounds, `until_unix` and `message_index_until` become exclusive upper bounds, and `archived` becomes `equals`, which excludes a null archived value for either boolean. `per_conversation_limit` becomes `group_by=conversationId` with that `per_group_limit`. `SearchConversations` returns no results for an unregistered collection and registers nothing. `SearchWithinConversation` registers the collection, scopes the search to one conversation id, and reads its fingerprint through `GetCollectionItemState`. `TestGenericCollectionSearchParity` (`test/live/generic_collection_search_live_test.go`) compares both surfaces on real Milvus rows.
